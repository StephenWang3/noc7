# 使用说明

给 NOC 值班和结单人员用：从工单系统导出一张已结单的工单，生成故障报告，再按报告里的标记核实。全程在本机运行，真实工单和报告只放在仓库外的 `~/.noc7/`。

开发、测试和配置细节见 [README](../README.md)。

## 一次性准备

1. 安装 [uv](https://docs.astral.sh/uv/)，在项目根目录执行 `uv sync`。
2. 模型密钥只放在环境变量里，不写进配置、命令或文件：
   ```bash
   export DEEPSEEK_API_KEY=…   # 由团队密钥注入，不要贴到聊天或工单里
   ```
   没有密钥时也能用离线规则跑（见第 2 步），只是不出模型摘录的结论。
3. （可选）公司 Word 的页眉：在 `~/.noc7/report_profile/profile.json` 写 `{"company_name": "…", "logo": "logo.png"}`，logo 放同一目录。不配置时页眉留空。
4. 导出工单要用本机 Node.js（`npx`）和 Chrome 里的 Playwright 浏览器扩展，并且在 Chrome 里已登录 NOC。

## 第 1 步：从 NOC 导出工单

导出只读，不点业务按钮，不保存 cookie。完整规则见 [导出说明](../scripts/noc_export/README.md)。

1. 在 `~/.noc7/real/plan.json` 写一个查询任务（`kind: "list"`，填时间范围、标题关键词等），运行：
   ```bash
   uv run python scripts/noc_export/exporter.py run --plan ~/.noc7/real/plan.json
   ```
   结果在 `~/.noc7/real/candidates.json`。
2. 从候选里挑出要的工单行，整行复制进新的计划（`kind: "export"`），再运行同一条命令。
3. 校验导出的工单包：
   ```bash
   uv run python scripts/noc_export/exporter.py validate
   ```

每张工单导出为 `~/.noc7/real/REAL-<代号>/` 一个目录，即“工单包”：字段、处理日志、邮件、附件都在里面，并带哈希清单。一轮最多 20 个任务；遇到限流、登录页或报错会立即停下，不会自动重试。

## 第 2 步：生成报告

对一张或一批工单包运行（`--out` 必须是仓库外**新的**目录）：

```bash
uv run noc7 analyze ~/.noc7/real/REAL-<代号> \
  --provider llm --model-config config/models/deepseek.json \
  --report-type closure --save-replay \
  --out ~/.noc7/reports-<日期>
```

- 路径写 `~/.noc7/real` 就是整批分析。每张单发 3 次模型请求，通常一两分钟；某张失败会继续下一张，最后退出码非零。
- `--report-type closure` 让核对报告的标题为“结案草稿”。不加时为“阶段报告”，内容相同。
- `--save-replay` 保存模型结果。以后只改了本地规则，可以不花钱重放（见“报告不对时怎么查”）。
- 没有密钥时把 `--provider llm --model-config …` 换成 `--provider rules`，用离线规则跑。

### 用网页操作台（推荐演示时用）

```bash
uv run noc7 serve
```

浏览器打开 <http://127.0.0.1:8765>。第一页有四个标签：

- **本机工单**：列出 `~/.noc7/real` 下导出的工单（启动时可用 `--local-root` 换目录）。勾选几张，选“规则”或“用模型分析”，点“分析选中的 N 张”，进度条实时显示完成、失败、剩余；逐张按顺序分析，先完成的可以先点“查看”。
- **演示单与导入**：五张合成演示单，以及上传一个 zip 工单包。
- **分析记录**：做过的分析按完成时间倒序，能直接打开七要素、公司报告或下载 Word。用模型分析过的结果在重启后保留。
- **由 NOC 工作台传入**：给工作台嵌入用。

选好一张后翻到第二页看七要素和原文出处，第三页是公司报告预览和 Word 下载。用模型分析需要启动前在同一终端设好 `DEEPSEEK_API_KEY`。页面只监听本机，结果存在 `~/.noc7/demo-inbox`。

## 第 3 步：看报告

每张工单在输出目录下有一个子目录：

| 文件 | 给谁看 | 内容 |
| --- | --- | --- |
| `company_report.docx` | 交付、存档 | 公司格式故障处理报告；`company_report.html` 是同样内容的网页预览 |
| `report.html` / `report.md` | 核实的人 | 核对报告：七要素的全部候选和出处、处理时间线、待核实清单、材料完整性、证据原文索引 |
| `analysis.json` | 系统对接 | 七要素结构化结果，格式见 `schemas/analysis-result.schema.json` |
| `replay.json` | 重放 | 加了 `--save-replay` 才有 |

公司报告的每个结论都来自原文：核对报告里能按证据编号（如 `M02/log:5`、`M41/log:20`）找到原句。

## 第 4 步：按标记核实

系统的原则是“有值比空着好，但按准确度一层层取”：高一层没有可用依据才取下一层，低层取到的值一律标出来，交给人核实。

| 报告里看到 | 意思 | 要做什么 |
| --- | --- | --- |
| 正常填写，无标记 | 原文有明确依据（客户确认、RFO、处理日志等） | 抽查即可 |
| `【待核实】` 或 `【待核实：…】` | 依据较弱，或有冲突、只精确到日、恢复未确认等，括号里写了原因 | 按核对报告里列出的候选和原文判断 |
| `【日期按…推定】` | 原文只写了时刻没写日期，按该条日志的记录时间补了日期 | 确认日期 |
| “兜底，待核实：…取自工单系统…字段” | 原文里没有可用的说法，取了工单系统字段 | 确认字段值是否就是本次故障 |
| 责任方“按供应商 RFO 所述…推定为供应商”“按割接通知推定为供应商” | 原文没直接写谁负责，按 RFO 原因或割接通知推定 | 确认推定是否成立 |
| 空着 | 原文没有可用依据。系统不猜 | 有其他材料的人工补 |
| 只有一行“本单…不是业务故障，不出故障报告” | 原文写明是割接、测试、误报等，不是故障 | 确认确实不是故障 |

各要素取值的先后顺序：

- **恢复时间**：业务记载（客户、供应商 RFO、联通日志）→ 按北京时间推定 → 告警清除 → 客户确认 → 工单系统恢复时间字段。
- **责任方**：原文明确写的 → 按 RFO 故障原因或割接通知推定 → 原文写“怀疑”的。供应商所说的故障时刻（写明北京时间的）和本次中断对不上的，不作依据。工单系统“故障区域”字段不作责任依据。
- **故障地点**：城市 → 省州 → 线路段（两端地名）→ 国家 → 工单系统故障地址字段。只写站点、距离或坐标的留空。

原文明确否定的（如“经核查非我方原因”）不会被兜底成该方。

## 报告不对时怎么查

1. 先看 `report.html` 里该要素的“候选与观测”：有哪些候选、各自出处、为什么没选上。
2. 想看模型原样返回了什么、本地规则丢了哪条，重新分析时加 `--model-audit-dir ~/.noc7/audit-<日期>`（必须是新目录）。里面有原始响应和本地裁决前后的记录。
3. 只改了本地规则时，用保存的模型结果重放，不调用模型、不花钱：
   ```bash
   uv run noc7 analyze ~/.noc7/real --provider replay \
     --replay ~/.noc7/reports-<日期> --out ~/.noc7/replayed-<日期>
   ```
   只有改了提示词才需要重新调用模型，并且只重跑受影响的工单。

## 数据安全

- 真实工单、报告、审计记录只放在 `~/.noc7/` 等仓库外目录。程序会拒绝把真实数据写进仓库。
- 发给模型的只有带编号的文字片段（含本地 OCR 出的文字），不发原始截图。默认只发官方 DeepSeek 接口；换成内网 Qwen 只需换一份配置，见 [README](../README.md#文本模型与配置切换)。
- 密钥只从环境变量读，不要写进任何文件或命令行参数。
