# 0007 报告对齐公司故障报告格式并导出 Word

- 日期：2026-10-27
- 阶段：A1 报告层（联调后）
- 状态：已采纳
- 相关：PRD 报告章节、ADR 0001（方案 A）、ADR 0006、`CONTRACTS.md`

## 背景

`noc7 analyze` 原来只生成 `report.md` / `report.html`。这两份是审核报告：除了七要素，还列出证据编号、候选值、待核实清单和材料完整性。公司内部流转的是另一种格式，即 Word 版「故障处理报告 Failure Report」。

用户给了两份真实样例：一份老版 .doc 空白模板（2023 年），一份按同一模板填好的 .docx（以下称 A05）。两份的栏目和版式一致，以 A05 为准。原件只放在本机 `~/.noc7/real/report_samples/`，不进仓库。

模板结构如下：

- A4 纵向，页眉放公司 logo 和公司名。
- 标题「故障处理报告 Failure Report」，下一行右对齐写日期。
- 一张 11 行 × 4 列的中英双语表格：
  - 首列「故障基本情况」竖向合并 7 行，包含客户名称、电路编号、故障号、业务类型，以及「故障时间」下的申报时间、恢复时间、故障历时（GMT+8，单位分钟）。
  - 后 4 行依次是故障现象、处理过程（每行「时间 GMT+8 内容」）、故障原因分析、改进及预防措施。
- 表格下方是报告人、审核人、审核日期三行签名。

七要素里的「责任方」「故障位置」在模板中没有栏目；模板里的「改进及预防措施」在七要素中没有来源。

## 可选方案

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A | 用 python-docx 在代码里排出同样的表格 | 依赖已在 A0 声明，不改 pyproject/uv.lock；仓库里不放二进制模板；只用合成数据就能测；版式改动在 diff 里看得见 | 字体、行高等细节要逐项写；与原件像素级一致做不到 |
| B | 仓库放一个 .docx 模板，按占位符填写（docxtpl） | 改模板不用改代码 | 要新增依赖，违反 A0「运行依赖一次性声明」的约定；二进制模板在 git 里看不出改了什么 |
| C | 直接拿 A05 原件当底板填写 | 样式和原件完全一致 | 测试离不开仓库外的真实文件；原件里的真实内容可能残留到输出里 |

用户已确认三点：

- 公司格式作为新增输出，审核报告保留。
- 「改进及预防措施」默认填公司通用套话，并标成待审核。
- 责任方和故障位置并进「故障原因分析」栏。

## 选择及理由

选方案 A。代码在 `src/noc7/report/company.py`：

- `LAYOUT` 逐格描述 11 × 4 表格：合并范围、双语标签段落、取值键。Word（`write_company_docx`）和网页预览（`render_company_html` + `company_report.html.j2`）共用这一份描述，两种输出不会走样。
- `write_reports()` 在原有四个文件之外，再写 `company_report.docx` 和 `company_report.html`。两者的输入是同一份校验后的 `AnalysisResult`，不重新抽取、不调用模型。

各栏取值规则：

| 栏目 | 来源 |
| --- | --- |
| 客户名称 | 工单字段 `customer`（从 `ticket_fields` 材料的 `f:<key>` 片段读取，不写死 `M01`） |
| 电路编号 | `circuit_id`；有 `circuit_id_new` 且值不同时写成「新：X；原：Y」 |
| 故障号 | `ticket_no`，没有就用 `ticket_ref` |
| 业务类型 | `business_type`（真实导出才有，不在 `KNOWN_FIELD_KEYS` 里，不改共享 schema），没有就用 `fault_type` |
| 申报时间 / 恢复时间 | 七要素的发生时间 / 结束时间，格式化为 `YYYY-MM-DD HH:MM:SS (GMT+8)` |
| 故障历时 | 沿用 `final_duration()`：只有恢复有确认依据才写确定值，四舍五入到整分钟 |
| 故障现象 | 七要素的现象结论 |
| 处理过程 | 处理过程步骤，每步一行「时间 GMT+8 处理人 动作，结果。」。跳过重复步骤，计划步骤加「（计划）」 |
| 故障原因分析 | 原因结论；另起一行「责任方：…；故障位置：…」 |
| 改进及预防措施 | 公司通用套话 + 「【系统默认表述，待审核】」 |
| 报告人 / 审核人 / 审核日期 | 留空，由人填写 |
| 报告日期 | 生成时间，换算成 GMT+8 |

待核实的规则：凡是系统拿不准的地方，都写黄色高亮的「【待核实…】」（网页里用 `<mark>`），不填看似确定的值。

- 状态是 `unknown`，写「【待核实】」。
- 状态是 `conflicted`，写「【待核实：有冲突】」。按 schema，`conflicted` 的结论值必须为空，所以没有当前值可写。
- 时间无法解析、只精确到日或时区未知时，保留原文，并加对应标记。
- 起止时间都有、但恢复没有确认时，写「约 N 分钟【待核实：恢复未确认】」。
- 工单已撤销时，历时只写「【待核实】」。

页眉：公司名和 logo 出自真实样例，按真实内容处理，不进仓库。代码只读本机 `~/.noc7/report_profile/profile.json`（字段 `company_name`、`logo`），环境变量 `NOC7_REPORT_PROFILE` 可以改目录。没有配置时页眉留空，配置里写了 logo 但文件不存在时直接报错。测试的 `conftest.py` 一律把这个目录指向空目录，测试结果不受本机配置影响。

## 后果与代价

- 版式由 `scripts/check_company_report.py` 对照。它只比较行列数、合并结构、13 个栏目标签、标题和签名栏，不打印单元格内容，所以可以直接拿本机的 A05 对照。合成和真实输出对照 A05 都是 0 差异。
- 与原件的已知差异：
  - 行高没有逐行固定，Word 会按内容自动撑开。
  - A05「故障号」格里嵌套了一张空表，这里没有复刻。
  - 页眉下划线没有复刻。
  - 真实工单的现象和处理过程是原文，可能带整段邮件或 `<br>` 字样。报告层不改写原文，精简要靠抽取层，或者由人在 Word 里改。
- 「改进及预防措施」永远是套话加待审核标记，系统不对改进措施做判断。以后如果要生成针对性建议，要另走模型调用、外发闸门和评测。
- 报告日期和时间口径固定为 GMT+8，与公司模板一致。如果以后要出其他时区的报告，要改 `REPORT_TZ` 和 `gmt_label` 的调用方式。
- 不支持导出老版 .doc；Word、WPS、Pages 都能打开 .docx。
