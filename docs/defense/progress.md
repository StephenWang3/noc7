### 遇到的问题和解决办法

1. **A1、A2 并行开发怎么不打架。** 按材料类型分工，证据编号带材料前缀（`M03/msg:1`），两条线只交换证据片段；默认注册表按包名自动加载，未交付的一方由“不支持”兜底。外发闸门和运行依赖都提前放进 A0。详见决策 0003。
2. **标准答案不能和解析器的实现绑定。** 写标准答案时还不知道解析器会怎么切片段，所以证据用“锚点”（材料 + 字段/处理过程序号/邮件消息/页码）表示，文本按要点判分。`noc7 gold check` 会核对每个锚点真实存在。
3. **“原因栏”“责任栏”不能直接照抄。** 起初只想用一个 `cause` 字符串，写 S02、S05、S09 时发现原因栏分别是计划割接、可能原因清单、排查结论。改为“候选 + 类别”，只有确认或某方陈述的根因、计划作业能成为结论，规则写进校验器，模型输出不合规会直接被拒绝。
4. **时间的时区。** 源系统字段没写时区，但口径是 GMT+8；上游邮件用 UTC；海外设备日志完全没写时区。做法：工单包声明 `default_timezone`，按它解析的时间标 `assumed`；原文写明的标 `explicit`；不根据城市猜时区。`TIME_TZ_MISSING` 只在时间明显是另一种口径时报，否则每张单都会报十几条，审核人员会忽略。
5. **合成数据不能像真的。** 编号统一 `SYN-`；IP 只用文档保留网段，域名只用 example 域；这些检查写成测试，以后新增样本也会被检查。
6. **附件标志不可靠。** S10 的处理过程顶层“有附件”为 false，实际有一张截图。工单包按条登记实际附件，标志只留档，不一致时导入层给提醒。

### 失败的尝试和修正

- 时间解析最初的正则不认识“14时38分”这种只有时分、没有秒的中文写法，测试发现后修正；
- 合成数据检查一开始把 `attacker.example`（保留顶级域）和邮件地址里的 IP 误判为真实数据，调整了规则；
- 标准答案的“候选类别”起初是单个值，但同一个候选常常可以合理地归到两种类别（例如客户报告时间也可以看作邮件时间），只认一种会误判，所以在写标准答案前改成可接受类别列表 `kind_in`，并校验每个类别都是已定义的枚举值；
- P04 的处理过程最初没有按时间排序，发现后按记录时间重新编号。

### 需要用户或业务方确认的事

- 标准答案由编写合成样本的 agent 标注，**责任和原因的判断口径需要懂业务的人复核**；
- `docs/IMPLEMENTATION_PLAN.md` 是早期输入文档，里面的工作日估算没有改（本次只按要求修改了 `ARCHITECTURE_OPTIONS.md`）。

### 实现中解决的问题

1. **页面“查看”也可能写数据。** 通用工单详情的查看邮件方法会更新日志完成时间。脚本不调用这个方法，使用精确路径和方法白名单；POST 详情读取仍允许，但更新、发送、流转和报告操作没有入口。
2. **附件顶层标志会漏件。** 不以 `hasAttachments=false` 跳过。业务单的两类详情逐页、逐条读取表单，并下载实际文件；直接日志附件、邮件附件也读取。只按精确且唯一的处理人/时间匹配归属，失败就保留来源索引，不猜测挂在哪条过程。
3. **文件落盘和已有浏览器工具存在限制。** 工具的文件输出只允许工作区，而真实数据不能放工作区；Playwright 代码执行环境也不提供文件系统导入。普通运行以 stdio MCP 直接在本机 Python 接收；本轮已有共享会话使用随机令牌保护的回环接收器，正文不经聊天输出。接收器已关闭，连接令牌文件已删除。
4. **只读不等于接口稳定。** 实查发现单独传截止时间时服务端可忽略该条件，因此脚本要求时间查询起止成对，还核对返回行是否落在范围里。详情分页检查总数、空页和重复记录，截断即失败；未知附件控件也不能静默通过。
5. **失败不能变成看似完整的样本。** 先写私有临时目录，经现有加载器校验后原子发布；失败状态保留在本机。附件文件名只做描述，本机路径使用安全序号；输出父目录和符号链接都复核，不能绕回代码仓库。
6. **频率要有可执行上限。** 始终串行，默认至少 1500ms 加随机延迟，20 秒超时；一轮默认 300、最高 500 次读取。遇到 429 等错误立即停止，没有自动重试。查询计划显式列出工单或指定页，不扫描整个工单池。

### 仍需补齐

真实 PDF 的电子、扫描、混合页样本仍缺失；现有代码可以保留并基本验证 PDF 原件，但本轮没有真实 PDF 可验证。含未核实附件的流程单会停止；网络故障单一律拒绝完整发布。首轮作废单虽然读取了字段和五条过程，但不能据顶层空标志断言没有其他附件，已在评审修正中隔离。源系统隐藏资料、稳定生产 API 和批量同步规范没有在本任务中解决。

来源存档属于审计材料，不是新的独立佐证；原邮件、引用、日志复制和存档中的重复内容不能增加证据权重。工单包校验通过也不意味着七要素或故障结论已被业务确认。

### 问题、修正与取舍

1. **真实可运行但不依赖外部模型。** `rules` 做保守基线，`replay` 保存抽取结果并绑定输入/证据两份哈希；模型服务不是演示和测试的前置条件。设计论证见决策 [0005](../decisions/0005-text-extraction-validation-and-replay.md)。
2. **恢复确认不能只看单个词。** “同意结单”不提升恢复状态；“客户尚未确认恢复”不能命中正向确认。客户确认恢复但根因尚未查明时，恢复仍可成立，原因继续未知。
3. **跨日日期不能直接照邮件头。** UTC 邮件头的日期可能比 GMT+8 正文小一天。补齐裸时刻时先按正文明确时区换算日期；海外设备日志没有时区就保留 unknown，不按城市猜测。
4. **输出转义要测试实际模板名。** `.html.j2` 没有被按 `.html` 后缀判断的自动转义覆盖，恶意标签测试发现后改为按导出格式显式开启。Markdown 同时转义 HTML、链接及图片语法。
5. **A2 不需要修改 A1 入口。** A2 只产 `EvidenceSpan`，默认注册表自动发现；A1 已用合成结构化曲线片段测试分类别统计和首次非零候选，不声称已实现图像识别。低质量、失败、不支持各自有状态和提示。
6. **质量阈值与语言覆盖的代价。** 暂用 0.7 作为保守复核阈值（工程判断），不是已校准概率；复杂表达可能漏抽，现有问题提示也可能偏多。真实标注集到位后需要校准规则、阈值和模型。

### 取舍、局限与答辩表达

为什么用 python-docx 在代码里排版，而不是放模板文件或直接用原件填写：要守住「不新增依赖」「仓库里没有二进制模板和真实内容」「只用合成数据就能测」这三条，详见 [ADR 0007](../decisions/0007-company-report-format.md)。

公司格式报告是给人流转的终稿底稿，审核报告是给人核对证据的工作稿，两者来自同一份校验后的结果。高亮标记的作用是让审核人知道哪里要改，而不是把未知伪装成结论。所以真实工单中历时、恢复时间大面积待核实，这反映的是恢复确认材料不足（ADR 0006 已记录），不是格式层的问题。

局限：

- 现象和处理过程沿用抽取原文，真实单里会带整段邮件或 `<br>`，篇幅比 A05 长很多。
- 「改进及预防措施」不做针对性判断。
- 与原件的行高、嵌套空表、页眉下划线等细节没有逐项复刻。
- 版式一致只说明格式对齐，不说明各栏内容正确；内容是否正确仍要靠已结案工单的人工结论来评测。

## 已结案工单的人工参考评估

用户确认正式报告和明确人工结案结论都收集，并按来源分层。实现独立 `noc7.evaluation` 模块：参考原文转录与锚点核验、截止前材料包重建、规则基线、带输入／证据快照校验的结果导入和确定性评分。参考及同义词在查看提取输出前冻结，不改共享 schema、原始工单包、合成 gold 或提取规则。

只读核对二十张已结单候选及其已有报告记录，报告记录均空；公司 DOCX 样例能匹配具体工单，电路编号差异为空格。七例形成候选标注，引文要点均可核对，七例全部进入评估。已确认审核人空白不能当作已审核，供应商声称不能因进入正式报告而升级为确诊。

以最早的结案动作为截止，包含实际写下结案意见的销障；该条及不早于它的日志不进入输入。最终字段缺历史默认排除；参考锚点、副本、报告标记、AI 摘要、源留档及时间／归属不明材料隔离，提取器只读取新建输入包。可支持性与被测提取器分开，避免漏识别被误当成“输入无依据”。

七例共十一条参考事实：三条一致、两条遗漏、一条待判定、五条未确认输入支持。一致率 3/5，可判定覆盖率 5/6，均为小样本参考一致性指标，不能当作业务正确率。恢复时间和模块原因虽有原文支持，当前规则只保留候选而未输出结论；处理过程的冻结动作要点能够覆盖。未命中的同义改写不在看到结果后补标，责任方等无参考覆盖的要素不报告准确率。新纳入的一条现象没有截止前依据，没有进入一致率分母。

全量 306 项测试通过，浏览器只读边界、schema 与合成 gold 引用检查通过；真实基线成功，重复评分一致。原件、标注、映射和长篇明细留在仓库外 `~/.noc7/real-eval/`，本机目录与文件采用私有权限；提交的 [脱敏汇总](../HUMAN_REFERENCE_EVALUATION.md) 只保留计数与语义类别。设计取舍见 [ADR](../decisions/human-reference-evaluation.md)。

### 审核修订：否定范围、销障截止和日期时区

- 否定只认紧贴要点的词，并看要点之后、逗号之后的同一小句。英文否定在去掉空格之前按词边界判断。落在否定范围内的命中记为待判定，不再算一致；「无线」「排除故障后」这类前缀不再把引文里的要点整段否决。
- 销障纳入结案动作，截止取最早一条。该条及更晚的日志不进入输入。用原标注重新隔离和评分后，两例合计多排除 3 条签收前日志；已有事实的锚点数量和评分没变。
- 只有日期的参考时间按工单默认时区折到当地日期再比。跨过日界的 UTC 时刻不再按字符串前 10 位算同一天；时区不能确定则待判定。
- 修订后全量 `uv run pytest -q` 为 306 项通过。七例基线与两次评分的白名单计数一致。
