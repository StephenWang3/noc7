## 0. 结论先行

**推荐方案 A：独立运行的轻量单体系统，“证据优先”流水线。** 用一个 Python 进程完成导入、解析、抽取、校验、报告和审核界面；数据存在 SQLite 和本地文件里；模型和 OCR 统一走可替换的适配层。AI 服务还没批准时，先用“纯规则基线”和“录制回放”两种不调用外部服务的模式开发。

一句话理由：课题要证明的是“杂乱工单 → 带证据的七要素 → 校验 → 标准报告”这条链路能跑通、可以核对、效果可以量化。方案 A 用最少的基础设施覆盖整条链路，而且核心算法写成独立的包，以后要扩展成方案 B 的生产形态，不用推倒重来。

| | A 轻量单体（推荐） | B 生产级试点（现有实现计划） | C 嵌入 NOC 的增强插件 |
| --- | --- | --- | --- |
| 形态 | 独立 Web 应用 + 命令行 | 前后端分离 + 队列 + 数据库服务 | 浏览器扩展，在 NOC 页面里运行 |
| 技术栈 | Python、FastAPI、Pydantic、SQLite、Jinja2 + HTMX | React/TS、FastAPI、PostgreSQL、Celery/Redis、Docker | 浏览器扩展（TS）+ 本地/内网抽取服务 |
| 覆盖课题目标 | 完整 | 完整 | 依赖 NOC 现有报告功能，未验证 |
| 预估工作量 | 约 12–16 个工作日 | 20–27 个工作日（原计划） | 无法估算，前置条件不明 |
| 运行依赖 | 一条命令启动，无外部服务 | 4–5 个服务容器 | 生产 NOC 登录态 + 扩展安装权限 |
| 主要风险 | 并发和多用户能力弱 | 基础设施工作挤占核心算法和评测时间 | 需要往生产 NOC 写入；页面一改版就失效 |
| 答辩呈现 | 本地完整演示，可离线 | 同 A，但部署环节多、容易出故障 | 观感好，但演示依赖生产环境 |

## 2. 三个方案都要遵守的核心设计（与方案选择无关）

不论选哪个方案，下面这条流水线都不变。它是课题的“算法本体”，也是答辩要讲的主线。

```text
工单包（字段 + 处理过程 + 邮件 HTML + 附件）
   │ ① 导入：校验、内容哈希去重、记录来源和抓取时间
   ▼
① 解析：每种材料一个解析器，统一输出“证据片段 EvidenceSpan”
   ├─ 结构化字段 / 处理过程   → 每个字段、每条过程一个片段
   ├─ 邮件 HTML / EML         → 按消息边界切开，区分当前消息和引用；签名、免责声明打标
   ├─ PDF / DOCX              → 文本层优先，没有文本层的页走 OCR + 版面识别
   └─ 图片                    → 先判断类型（监控曲线 / 文档长图 / 现场照片 / 终端截图）再分别理解
   ▼
② 抽取：模型只能读带编号的证据片段，输出七要素“候选”，每个候选必须引用证据编号
   ▼
③ 校验：确定性规则（Python 代码，不交给模型）
   ├─ 证据编号是否存在、引用的原文是否真在该片段里（防止编造）
   ├─ 时间：先后顺序、负历时、未替换的 {{end_time}} 占位符、时区缺失
   ├─ 语义：“原因”到底是根因、候选清单、排查结论、恢复方式还是资源状态
   ├─ 去重：引用的邮件、AI 追单摘要、共用告警流水号的工单，都不算独立证据
   └─ 身份：新旧编号、带宽、拆机/撤销冲突 → 标“服务身份待核”
   ▼
④ 融合定值：每个要素得到 value + status + candidates + evidence_refs + issues
   ▼
⑤ 人工审核（接受 / 改写 / 清空，并写理由）→ ⑥ 报告：JSON、Markdown、HTML
```

### 2.1 关键设计决策和理由（答辩素材）

| 决策 | 理由 | 放弃的替代做法 |
| --- | --- | --- |
| **证据优先**：先把所有材料切成带编号的片段，模型只能引用编号 | 每个结论都能点回原文，编造的内容也能用程序查出来。调研发现七要素经常不能照抄栏位（调研 §4），必须看到依据 | 把全部原文塞给模型直接要七要素：结论无法溯源，幻觉也查不出 |
| **规则校验用代码写，不交给模型** | 时间先后、占位符、证据存在性这些判断是确定的，用代码写可测、可解释，答辩时也说得清 | 让模型“自查”：结果不稳定，无法写成回归测试 |
| **每个要素都有状态**：documented / confirmed / unknown / conflicted | 课题的难点是“不能填满七栏”：没恢复的单结束时间就该空着，没定责的单责任方就该未知（S01、S04） | 只输出一个值：无法区分“系统里记了”和“有人确认过” |
| **候选并存**：冲突时保留全部候选，不静默选一个 | S06 一张单里有 86%、10%、ping 中断三次丢包观测；S10 一张单有三个起障时间候选 | 取最早或最新的值：会丢失语义，把错误藏起来 |
| **时间带类型**：区分事件时间、记录时间、告警时间、确认时间，并记录原文、时区和精度 | 字段起止时间差和“返单历时”经常对不上（S02、S06、S09） | 只用一个时间字段 |
| **地点带角色**：业务端点、告警位置、测试节点、已定位的故障点 | 调研中没有一张单真正定位到故障点，业务端点不等于故障点 | 有地址就填 |
| **图片先分类再理解** | 附件里既有监控曲线（A），也有拼接的交付文档长图（B）；用途不同，能证明的东西也不同 | 所有图片一律当“故障截图” |
| **附件逐条枚举，不信 hasAttachments 标志** | S10 的标志是 false，实际却有附件 | 只看日志顶层的附件标志：会静默漏图 |
| **模型输出的内容一律当数据**，不当指令 | 邮件和附件里可能夹带“忽略规则”之类的文字 | — |

## 3. 方案详述

### 方案 A：独立运行的轻量单体系统（推荐）

**形态**：一个 Python 包 `noc7`（核心算法，不依赖任何 Web 框架），外加两个入口：

- 命令行：`noc7 analyze bundle/ --out report/`，用于批量跑评测，也是答辩现场的“兜底演示”；
- Web：FastAPI 提供上传、分析和审核三栏界面（左：材料原文预览；中：七要素与时间线；右：缺失和冲突清单），点击任一要素即可高亮原文片段或图片区域。

**技术栈与理由**

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 语言 | Python 3.11+ | 文档解析、OCR、模型 SDK 的生态都在 Python；全程一种语言，答辩时容易讲清楚 |
| 数据结构 | Pydantic v2 | 七要素 schema 既用来约束模型输出，也用来校验和导出 JSON Schema，一处定义多处使用 |
| Web | FastAPI + Jinja2 模板 + HTMX，少量原生 JS 做图片区域高亮 | 不需要单独的前端工程和构建链；审核界面是“表单 + 局部刷新”，HTMX 足够用 |
| 存储 | SQLite + 本地文件目录（原始材料按内容哈希存放） | 无需额外服务；分析结果本身就是 JSON 文档，SQLite 只存索引、运行记录和审核修订 |
| 异步 | 进程内后台任务；每个材料单独记录解析状态 | 单人使用，一单几个附件，不需要分布式队列；失败的材料可单独重试 |
| 解析 | 标准库 `email`（EML）、BeautifulSoup（邮件 HTML）、PyMuPDF（PDF 文本层和页面渲染）、python-docx | 都是成熟的本地库，不外发数据。具体版本在实现时锁定 |
| 本地 OCR | RapidOCR / PaddleOCR 二选一，实现时用样本对比后定 | 中英文混排效果好，可完全离线；只用作基线和兜底，最终可换成公司批准的服务 |
| 报告 | Jinja2 模板 → Markdown / HTML；HTML 输出前转义 | 模板只读取校验后的 JSON，报告里的每个事实都能追溯 |
| 测试 | pytest + 合成工单包作为测试夹具 | 规则和流水线可以做回归测试，评测脚本也复用同一批数据 |

**优点**：链路完整，启动简单（`uv run noc7 serve` 一条命令），可离线演示；把时间花在课题真正的难点（证据融合、校验、附件理解、评测）上，而不是部署和运维。

**缺点和对策**：
- 不支持多用户并发和权限 → 目前定位就是单机、绑定本机，PRD §10 已经允许这样做；
- SQLite 和进程内任务不适合规模化 → 核心包 `noc7` 不依赖存储和任务框架，以后可以替换成 PostgreSQL 和 Celery，也就是演进到方案 B；
- HTMX 界面的交互上限比 React 低 → 对审核工作台来说够用；真不够时，后端 API 不用改，只换前端。

**预估**：约 12–16 个工作日，拆分见 §6。

### 方案 B：生产级试点（即现有实现计划）

**形态**：React + TypeScript + Vite 前端；FastAPI 后端；PostgreSQL；Celery + Redis；Docker Compose 部署。

**优点**：多用户、审计、权限、长任务队列都有现成方案，可以直接对接试点上线。

**缺点**：
- 课题的核心在算法和证据链，B 的大部分额外工作量（大约 8–11 天）都花在基础设施上，而这部分在答辩里不是得分点；
- 演示环境需要启动 4–5 个容器，现场出故障的环节多；
- 前提尚不具备：生产接口、服务账号、组织权限、正式模板都没有，P1 的连接器和权限映射现在只能空着。

**适用**：确认马上要进入真实试点，并且公司已经提供部署环境和数据接口。

### 方案 C：在 NOC 现有“业务故障报告”上做增强（浏览器扩展）

**形态**：一个浏览器扩展。在 NOC 工单详情页里读取字段、日志、邮件和附件，送给本地或内网的抽取服务，再把结果填进 NOC 的“业务故障报告”页面。

**优点**：用户无需切换系统，数据入口最自然，观感好。

**缺点（目前是致命的）**：
- **前提不成立**：现有报告功能的格式、字段和生成算法都没验证过（调研 §6，生成记录为 0）；
- **必须往生产系统写入**：生成、保存报告都是写操作，违反目前的只读约束，还要业务方授权；
- **没有接口契约**：页面路由和 iframe 结构一改，扩展就失效；
- 答辩演示依赖生产 NOC 的登录态，不能离线，也不便展示真实数据。

**适用**：业务方先提供现有报告的成品和模板，并授权在测试环境写入。可以作为方案 A 之后的集成方向：A 的输出 JSON 可以映射成 NOC 报告的字段。

## 4. 待回答问题 ①②：独立系统还是增强？数据怎么进来？

**独立系统还是增强现有功能**：先做独立系统（A）。理由有三：现有报告能力未知，在它上面做增强等于把课题建在一个未验证的前提上；增强必然涉及生产写入；独立系统的输出（结构化 JSON）以后能映射到任何报告模板，包括 NOC 自带的。答辩时可以把“与现有报告功能对接”列为后续工作，并说明原因。

**数据入口：统一成“标准工单包”**，所有入口都只负责产出这个包：

```text
bundle/
  ticket.json          # 基本字段、故障字段、列表状态与详情状态（两者都保留）、抓取时间、来源
  process_log.json     # 处理过程，逐条记录；每条的附件逐条列出（不依赖 hasAttachments 标志）
  emails/*.html|*.eml  # 完整邮件详情，不用列表里的摘要
  attachments/*        # 原始附件，文件名用内容哈希
  manifest.json        # 材料清单、哈希、预期数量（漏件时能发现）
```

| 入口 | 用途 | 现实程度 |
| --- | --- | --- |
| ① 合成工单包（仓库内 `fixtures/`） | 开发、测试、评测、答辩公开演示 | **立即可用**。按 S01、S02、S06、S10、X01 等调研样本的问题模式编写，不包含真实数据 |
| ② 手动上传 | 在 Web 界面上传 zip 包，或粘贴文本、上传附件 | 立即可用 |
| ③ 只读导出脚本（Playwright，用户本机运行） | 从已登录的 Chrome 读取 `esbProcess/*`、`busfault/download`，在本地生成工单包 | 技术上调研已验证可行，**需要用户同意后再做**；只读，输出只存本机，不进仓库 |
| ④ 正式接口连接器 | 生产自动同步 | 等接口和授权；导入层不用改 |

演示和答辩阶段用 ① + ②。③ 是否要做，取决于用户是否同意用真实工单（本机、不外发）做内部评测。

## 5. 待回答问题 ③：AI 服务未定时，模型和 OCR 层怎么设计

### 5.1 三个能力接口，多种实现

```python
class TextLLM(Protocol):      # 结构化抽取：输入证据片段，输出符合 schema 的候选
    def extract(self, spans, schema, prompt_id) -> RawCandidates: ...
class VisionLLM(Protocol):    # 图片理解：分类 + 结构化观测（曲线类别、单位、时间窗、极值；文档区域划分）
    def describe(self, image, task) -> ImageObservations: ...
class OCRLayout(Protocol):    # 文字与版面：文字块 + 坐标 + 表格结构
    def read(self, image_or_page) -> LayoutBlocks: ...
```

| 实现 | 是否外发数据 | 用途 |
| --- | --- | --- |
| `rules`（纯规则基线） | 否 | 只读结构化字段，用正则抽时间和指标。**无需任何 AI 即可跑通全链路**，同时是评测的对照组 |
| `replay`（录制回放） | 否 | 读取预先保存的模型响应，结果确定，可重复，用于测试和离线演示 |
| `local` | 否 | 本地 OCR（RapidOCR/PaddleOCR）；可选本地开源模型（OpenAI 兼容接口，例如 Ollama） |
| `openai_compatible` | 视配置 | 公司内网模型通常提供 OpenAI 兼容接口，改个配置就能接入；MiniMax 等外部服务也走这一路 |

### 5.2 数据外发闸门（硬约束，写在代码里）

- 每个工单包带数据分级：`synthetic`（合成）或 `real`（真实）；
- 每个服务提供方在配置里声明 `allowed_data: [synthetic]` 或 `[synthetic, real]`；
- 调用前由闸门检查：**把 `real` 数据发往未获批准的服务时直接拒绝并报错**，不提供“临时绕过”的开关；
- 默认配置里所有外部服务只允许 `synthetic`。公司批准某个服务以后，改一行配置并在决策记录里写明依据。

### 5.3 外部服务的限流

若以后批准使用 MiniMax OCR，适配器内置限流：每批 10 个请求，批间间隔 30 秒；遇到限流先等 5 分钟再重试，不立即重试。这些参数写在配置里，其他服务按各自限额调整。

### 5.4 抽取方式：分两步

1. **事件抽取**：按处理过程和邮件消息分块，抽成“时间 / 主体 / 动作 / 对象 / 结果 / 观测范围”的事件列表，得到时间线；
2. **要素归纳**：基于结构化字段 + 事件 + 图片观测，生成七要素候选。

理由：处理过程常有 15–24 条，而且大量重复（S02 同一结论复制了五次）。先抽事件、再归纳，一来上下文短，二来去重可以在两步之间用代码完成，三来时间线本身就是报告里的“处理过程”。

## 7. 待回答问题 ④⑤：答辩最能体现价值的部分，以及怎么评测

### 7.1 设计上优先保证的四个“答辩亮点”

1. **证据溯源**：每个要素点一下就能看到原文片段或图片区域；编造的引用会被拦截。这是“可信”的直接证明。
2. **冲突与未知识别**：系统主动指出“结束时间未知（未见恢复确认）”“原因栏只是排查结论”“三个起障时间候选”。这正是人工整理时最容易出错的地方，也是本课题和“简单填表”的区别。
3. **附件理解带来的增量信息**：用 S10 风格的样本展示，六类 QoS 丢包统计**只存在于截图里**，正文完全没有。用消融实验量化“去掉附件后哪些要素变差”。
4. **规则校验拦截**：时间倒置、`{{end_time}}` 占位符、AI 摘要重复计数、共用告警的关联单，现场演示被拦下来的情况。

### 7.2 评测样本

- **合成集**（可以公开展示）：按调研中观察到的 11 类问题模式编写，每类 1–2 张单，共 15–20 张，附人工标注的标准答案（值、状态、允许为空的字段、应当报出的冲突）；
- **真实脱敏集**（可选，需要用户同意）：用 §4 的导出脚本在本机生成，只在本机评测，不进仓库，不外发；
- 开发集和验收集按“事件”划分，共用一条告警的工单不能拆到两边。

### 7.3 指标

| 指标 | 定义 | 为什么要这个指标 |
| --- | --- | --- |
| 分要素准确率 | 标准答案有值时，抽出的值正确的比例（时间精确到分钟并核对时区；文本按要点覆盖判分） | 核心效果；七个要素分别报，不合并成一个数 |
| 未知识别率 | 标准答案为空时，系统也给空（或标 unknown）的比例 | 防止“为填满七栏而编造”，课题可信度的关键 |
| 编造结论数 | 根因、责任、结束时间在没有证据时却给出确定值的次数 | 目标为 0；单列，便于在答辩时说明 |
| 冲突检出召回率 | 标准答案里的冲突被系统报出的比例 | 体现规则校验的价值 |
| 证据引用正确率 | 引用的片段确实支持该值的比例（抽样人工核对） | 溯源不能只是摆设 |
| 结构合法率 | 输出通过 schema 校验的比例 | 目标 100% |
| 单张耗时 | 人工从零整理 vs 系统辅助（含审核修改时间） | 课题“减少人工工作量”的直接证据；小样本，只作参考 |

**对照实验**：`rules` 基线 vs 模型抽取 vs 模型抽取 + 规则校验，以及有附件 vs 无附件。这样能把“AI 带来了什么”“规则校验带来了什么”分开讲。

## 8. 实现过程中的思路记录（答辩准备）

- `docs/decisions/NNNN-标题.md`：每个设计决策一份，固定四段：背景、可选方案、选择及理由、后果与代价。本文中的决策会作为第 0001 号；
