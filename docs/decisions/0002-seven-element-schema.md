# 0002 七要素数据格式：状态 + 候选 + 证据，约束写进模型校验

- 日期：2026-10-27
- 阶段：A0
- 状态：已采纳
- 相关：`src/noc7/schema/`、`schemas/analysis-result.schema.json`、ARCHITECTURE_OPTIONS §2.1–2.2、PRD §2、§6

## 背景

“七要素”是起障时间、结束时间、故障现象、责任方、原因、处理过程、故障地点。调研样本说明，难点不在“把七栏填满”，而在**知道哪些不能填**：

- S01、S03：还在排查或挂起，结束时间、原因、责任、故障点都不存在；
- S02、S05、S07、S09：原因栏写的是计划割接、可能原因清单、排查结论（“本端无告警”），不是根因；
- S06、S09：责任栏或处理部门是供应商，但没有任何定责结论；
- S04：告警所在的槽位端口不是已定位的故障点；
- S06、S10：同一要素有多个互相矛盾的时间或观测（三次丢包、三个起障时间）；
- P01、P02：时间倒置、负历时、UTC 与 GMT+8 跨日、海外设备日志没有时区。

如果数据格式只有“一个值”，这些情况要么被静默填上，要么丢失。

## 可选方案

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 1 每个要素一个字符串 | `{"cause": "…"}` | 最简单 | 无法区分“系统记了”“有人确认”“不知道”“有冲突”；无法溯源 |
| 2 值 + 置信度 | 每个要素一个值和 0–1 的分数 | 常见做法 | 分数无法解释；“没有依据”仍然会给出一个值 |
| 3 状态 + 候选 + 证据，约束写进 schema | 每个要素有状态（documented / confirmed / unknown / conflicted），候选带语义类别，结论必须引用证据；关键业务约束由 Pydantic 校验器强制 | 能表达“不知道”和“有冲突”；每个结论可溯源；错误结构直接被拒绝 | 结构更复杂，抽取和界面都要处理候选 |

## 选择及理由

选 3。具体设计：

1. **状态**：`documented`（工单里有记载且有证据）、`confirmed`（有证据或人工审核确认）、`unknown`（不知道，值必须为空）、`conflicted`（至少两个互相矛盾的候选，值必须为空）。
2. **候选带语义类别**，结论值只能取允许的类别，由校验器强制：
   - 原因：只有 `root_cause_confirmed`、`root_cause_claimed`、`planned_work` 能成为结论；排查结论、可能原因清单、恢复方式、资源状态、处理阻塞、客户怀疑只能留在候选里；
   - 地点：只有 `located_fault_point` 能成为结论，告警位置、业务端点、客户现场、测试节点不能；
   - 责任：`inferred_from_role`（只因为是供应商或处理部门）不能成为结论。
3. **时间值** `TimeValue` 同时保存原文、ISO 值、时区来源（explicit / assumed / unknown）、偏移、精度和“是否为占位符”。不根据城市猜时区；`{{end_time}}` 这样的占位符保留原文、ISO 为空。时间候选有 22 种语义（`TimeKind`），区分事件时间、记录时间、告警时间、客户报告时间、确认时间、曲线首次非零等。
4. **证据**：结论和候选都必须引用证据编号；`AnalysisResult` 校验时检查每个引用都真实存在，编造的编号直接拒绝（`EVIDENCE_REF_MISSING`）。
5. **问题代码**：31 个固定代码（`IssueCode`），只增不改，规则、评测和标准答案共用。
6. 所有模型 `extra="forbid"`：多写一个字段也会报错，避免“悄悄加字段”造成两条开发线格式漂移。

## 后果与代价

- 抽取（A1）要输出候选并给每个候选选类别，比直接输出一个值难。好处是规则可以对类别做确定性判断，不靠提示词；
- 审核界面（A3）要展示候选和状态，不是简单的七个输入框；
- 约束写在模型上，**模型输出不合规时直接校验失败**，A1 需要设计“校验失败 → 降级为 unknown 并报问题”的兜底；
- `fixtures/examples/SYN-P04.analysis.json` 是一份手写的合法结果，A1 可以对照，A3 可以先用它做界面。
