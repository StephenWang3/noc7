# 0005：从共享 Chrome 只读导出本机真实工单包

日期：2026-10-27
状态：已实现；实查覆盖和缺口见 `docs/defense/progress.md` 的本阶段记录。

## 背景

用户批准导出此前调研的 11 张工单，再有限查找 PDF、EML 和明确作废样本。真实数据只能在 `~/.noc7/real/` 等仓库外本机目录，不进入项目、不交给外部模型；Codex 调试时允许看到部分内容。A1 文本链路、A2 附件链路正在并行，导出端只产出既定工单包。

已通过项目只读 git 核对 #2 调研分支和 #4 地基分支；现有 `docs/BUNDLE_FORMAT.md`、`src/noc7/bundle.py` 与 #4 一致。调研会话也没有留下工单编号映射，因此不能仅凭脱敏代号定位源系统工单。

## 决定

代码全部放在 `scripts/noc_export/`，测试放在 `tests/noc_export/`，复用现有工单包加载校验，不修改 schema、运行依赖、CLI 和 A1/A2 文件。

浏览器采集器只在用户共享的同一个标签页内运行，以同源 `fetch` 复用登录态，不复制 cookie，不启新窗口。每个路径与 HTTP 方法有精确白名单。允许经核实的详情 POST；拒绝新增、修改、流转、邮件发送、报告生成/保存等端点。原始材料里的脚本和链接不执行、不自动加载。

实查发现通用工单详情的 `openEmailDetailsDialog` 会调用更新日志接口。因此“查看”二字不能保证只读；导出端绕过界面方法，直接读取。业务单适配详情、过程日志、邮件日志、两类详情完整分页、每条表单及原始附件；自动大客户/中继/设备布局通过与 iframe 同源的已核实表单和日志读取接口适配。网络故障 3.0 只核实了字段和过程日志 GET；逐条详情和附件尚未核实，无法以空标志证明没有文件。采集和打包两端均失败并留本机记录，暂不发布完整包。出现未核实的流程附件或未知布局时也显式失败。

默认串行，每次请求开始至少间隔 1500ms，加 0–250ms 抖动；硬下限 1000ms，20 秒超时，一轮默认 300、上限 500 次请求。一次最多 20 个显式任务，查询每页最多 50 条、限制页码，详情最多 10 页。没有自动全库扫描、并发下载或无限重试。额外提供有限附件元数据预检：逐页读取详情及指定工单关联邮件，找到 PDF/EML 候选后才完整导出；预检本身不会发布为工单包。登录页、HTTP 错误、业务错误、分页截断、预算耗尽立即停止。发生 429 时不会自动续跑。

采集与打包分离。普通本机入口以 stdio JSON-RPC 调用本机 Playwright MCP，正文只在本机进程间流转；子进程的工作目录设为私有数据目录，让工具自动日志也写在仓库外。平台已有共享会话时，可使用只绑定回环地址、带随机令牌的临时接收器，避免将工单正文或附件 base64 输出到聊天。接收器不代理网络请求、不接受目标文件路径、不提供下载或浏览接口；退出删除连接信息。

打包先写 0700 临时目录，文件 0600。确认材料大小、哈希、处理过程引用及 schema 均通过 `load_bundle()` 后，原子发布为 `REAL-*`。失败材料留在本机隐藏临时目录或失败记录中，不冒充完整包。源附件名不参与本机路径构造；解析后的实际目录不能落在当前仓库或其他代码项目里，包括符号链接指向的路径。

## 原文与归属

字段原文、两种状态、原始日志、详情表单、邮件头/完整正文及附件分别保留。授权参数只在浏览器内临时使用，落盘前剔除。附件二进制不在原始响应存档中重复保存，原始字节以附件材料为准。JSON 存档也有清单和哈希。

不能只按 `hasAttachments` 决定是否查详情。两类详情都要逐页、逐条读取；有文件就下载。只按处理人和时间精确且唯一匹配日志；不沿用界面十秒容差，也不猜测归属。未匹配材料仍保存并指出详情索引。源系统无编号的邮件/内部记录排在编号过程后，另存原始索引到包内序号的映射，不冒充源显示序号。

业务单的完整详情整理为独立 text 材料，完整邮件整理为带头字段的 HTML；未经改写的源响应仍在包里。PDF、图片、DOCX、EML 做基本签名检查，未知格式保留为 other，不用后缀伪造格式。报告下载可能先保存，导出脚本没有报告生成/下载入口。

## 重新定位研究样本

将报告里的类型、当时状态、时间范围、记录数、特定内容组合用于有限查询。原编号没有留存，故本机索引记录 `alias` 与 `match`，说明是特征重定位；相似候选不直接升格为原样本。日志和状态会随时间变化，不能只用当前条数否决或认定同一张单。共享告警样本需再比对告警流水、设备、位置、设备告警时间，不能凭标题判断关联。

编号映射、实际查询计划、候选列表、匹配依据和执行记录只留本机。仓库文档只写脱敏覆盖和数量。明确作废与已撤销分别保留，不当作业务恢复，也不互相替代。

## 代价和边界

这仍是获准范围内的取样脚本，不是稳定生产接口或后台同步服务。工作台布局或响应结构改变后应显式失败、重新核实；不能猜接口继续。未核实附件存储方式的流程暂不声称完整支持；网络故障 3.0 一律拒绝完整发布。有限搜索没找到 PDF/EML，只能报告该次搜索未覆盖，不能推断系统不存在。

校验通过证明包的内部完整性，不证明源系统已经提供全部资料或故障结论正确。后续 A1/A2 仍要处理证据来源、冲突、解析失败和人工核对。

## 验证

`uv run pytest -q tests/noc_export`、`node tests/noc_export/test_browser.cjs` 验证目录隔离、路径穿越、虚假格式、漏件、附件标志失真、归属歧义、只读白名单、登录失效、分页截断、预算及 stdio MCP 交互。测试使用虚构数据，不连接生产系统。真实工单包通过本机 `exporter.py validate` 单独校验，不在 CI 中读取。


## 评审修正

邮件关联统一展开数组、拆分字符串并合并 `emailId`/`emailIds`；正文和 EML 附件共用同一份邮件到过程序号映射，映射同时覆盖过程日志和邮件日志。只有邮件日志中存在的记录追加在末尾；已有过程的相同记录视图不重复插入，两个源索引各自留档。纯文本邮件转义为 HTML，让它与 HTML 正文一样进入 `emails` 引用。

打包逻辑版本提升到 `PACKAGER_VERSION=3` 并参与包身份；先构建完整输出，经校验后比较既有清单，不一致就拒绝复用。仅以目录存在和内部哈希合法判断幂等是不够的：旧输出可能内部自洽，却不包含这次的修复。

首轮把网络单的空标志当作无附件依据，违反了逐条核实要求，已撤销此放行。该单的旧产物隔离在本机隐藏归档；其余 15 份用保存的响应及原附件字节离线重打，没有重新请求 NOC。历史结构校验不代表资料完整，本次记录明确区分两者。
