# 责任方与故障地点按业务口径进入正式报告

状态：已采纳。依据：用户转发的业务方答复，以及本任务确认卡对实现方式、责任分类、冲突和不足处理的确认。

## 问题与方案选择

此前模型两栏在 `separate_suggestions()` 中被清空，仅在审核报告作 AI 建议，公司报告正式值为空。本次比较了扩展本地句式规则、单次模型提交结构化业务关系、人工确认后再填入三个方案。用户选择结构化关系方案：模型解释语义，程序核验来源、引用、覆盖范围、候选关系及优先级；不增加第二次模型判断，也不根据真实工单补句式词表。

本决策取代 [AI 建议决策](ai-suggestions.md) 中“两栏不能自动进入正式结论”的边界；历史结果和记录保留原义，不自动升级。公司模板继续把责任方与位置列于原因分析内，不增加独立报告产品或人工审核操作界面。

## 关系与正式值

`PartyCandidate.party` 和 `LocationCandidate.description` 仍是原文摘录。新增 `PartyRelation`、`LocationRelation`，共同保存本次事件、范围、明确／推测／否定关系、原文断言、来源类别与出处引文、陈述方和矛盾候选。原文未署名可以保留空陈述方并披露，不能据此编造责任主体；来源层级必须有可核验的直接引文。

责任关系另存标准类别、业务路径、专门责任依据 `responsibility_quote`、客户侧设备故障前提、采购归属及相关动作锚点。正式责任只取 **客户、供应商、联通**；其他、共同责任和未知主体只保留候选。采购归属自身不是责任结论，客户侧设备故障也不能直接等同客户责任。

- 明确归属路径：仅允许 `basis=formal_determination`、`customer_device_fault is False`，且自查、供应商上门、联通上门三个动作锚点均为空；`claimed` 仅留候选。客户设备前提为真或未知时不能从该路径直接采用，必须满足相应上下文路径的全部条件。仍必须有专门责任依据，完整包含在关系上下文中，直接记载责任归属或某方所提供网络／设备发生影响本次业务的实际故障归因。出处引文只能证明信息来自谁，不能代替责任依据；只有供应商名称、一般反馈标题或客户侧排查范围不能定责。缺少该锚点保留候选，不从旧响应上下文自动补造。
- 客户侧设备故障、要求客户自查，完整已结单记录中未见后续追问：可采用客户责任。必须同时满足模型关系及本地输入覆盖条件；同候选或同事件同范围其他候选有可靠供应商或联通上门锚点时，不能采用客户责任，不以客户设备故障标志为真作为拦截前提；模型把路径标成明确归属也不能绕过该约束。
- 客户侧设备故障且仍联络供应商上门：可采用供应商责任，保留上门联络原文；不将“联络上门”说成“已到场”。
- 客户侧设备故障且联通分公司已上门处理并使业务恢复：可采用联通责任，必须同时有处理及恢复依据。供应商与联通上门锚点同时存在时，两条路径均留待核对，不能由模型所选路径决定责任。

地点关系保存城市、城市归属引文、已定位关系和城市范围。正式值必须 `city_scope=single_city` 并取原文明示的城市；`unknown` 和 `cross_city` 均不采用，即使粒度标成 city 也不能取跨城原文中的端点城市。不查地名库、不展开缩写、不凭端点猜城市。站点、设备、端口有明示城市归属时取城市；国家、跨城或范围不明的段落只保留候选。段落明确全部在同一城市内时可以取该城市。告警位置、业务端点、客户地址和测试节点不能靠模型选中就自动升级为故障点。

**补充口径（2026-11-12）**：原文没有可采用的城市、但写明故障点在某一个省、州（含整段线路都在同一个省、州内）时，填该省、州，保留原文的“省／州／Province”等字样并注明只到省、州一级；只要有可采用的城市就不取省、州，不论来源层级。跨省、州的段落仍不填。省、州级别由本地按名称和原文判定，不采用模型自报。

## 来源、冲突与输入覆盖

有效来源顺序为 **RFO → 供应商反馈 → 分公司处理日志**，按信息实际出处判断，不按文件载体机械降级。RFO 标题本身不证明责任或故障点已查明。来源分类、责任业务关系和城市定位的语义仍由模型判断，引用核验只证明文字存在，不证明判断正确。真实试跑发现仅有来源／路径标签仍可能把角色和客户侧现象误放为责任，因此明确归属必须另给专门责任锚点；这仍不能替代 NOC 人工审核。

只从本次事件的明确、有可靠直接依据的候选中选择最高有效层级；高层无效时可以采用有效低层。最高层同结论的重复候选不投票，确定性选首项；同层不同责任或城市、同层同事件同范围明确否定同一责任类别或城市且有可靠直接依据时（不要求填写 `contradicts` 编号），正式值留空并标冲突。跨层采用高层结论时保留低层差异和采用说明。不属于三个层级的来源、推测或证据不足保留待核对。

`BusinessCoverage` 仅由本地构建，记录详情状态、非摘要非空处理记录的内容哈希、实际覆盖的记录定位及关联材料覆盖标志。模型请求只接收由它计算的范围提示，不能提交本地覆盖或审核记录。清洗或裁剪导致任一完整记录缺失、尚未结单、关联材料没有可靠片段时，不允许使用“客户未再追问”路径。此范围仅限所提供工单包，不证明源系统没有遗漏历史消息；关联材料有可靠片段也不证明其每个附件区域都已理解。

## 核验、兼容与报告

复用 `match_quote()` 的严格与空白等价匹配，记录原文范围；候选原文、断言、上下文和动作／城市锚点均须有据。标准化责任类别和城市从关系中取值，不要求它们等于整段摘录。不存在的证据编号仍整单拒绝，包括异常原答内嵌的来源。两栏实质不匹配、非对象、无来源或关系不完整时保留原答及待核对记录，不能支撑正式值；来源全是 vendor／handler／handling_dept，或 a_end／z_end／device_location／device_name／region／shelf_slot_port 角色／端点字段时，在候选核验阶段留空待核对，不先填正式值再触发整单拒绝；其他要素及共享正式显式引文继续遵守原有拒绝规则。

关系编号修复同步映射矛盾引用；歧义、缺失或自指的矛盾编号不猜选。首次分析、完整证据再校验及 `AnalysisResult` 加载均调用同一业务约束函数，检查选择、状态、值、依据和说明。规则提供方和旧保存结果不重新解释；旧模型原答缺少新关系不会自动升级。

自动正式值最高 `documented`，不创建 `review`。审核 Markdown／HTML 展示路径、来源、原文和未采用原因；已正式采用的要素不重复列为待确认建议，原答仍在关系审计中。公司 HTML／Word 共用 `CompanyReport`，正式值显示来源和“有记录，未经人工审核”，继续由 NOC 工作台承担人工审核。

## 并行开发与验证

业务约束独立放在 `providers/responsibility_location.py`；共享 schema、提示词、解码、校验和报告只添加接入。时间解析及恢复来源判定算法不在本决策范围。`EvidenceSpan`、附件解析器和外发闸门不变；JSON Schema 随共享模型同步导出。旧审计回放允许缺少新增覆盖提示，但包哈希、证据哈希和原请求证据仍须严格一致。

验证包括合成业务反例、保存后复验、公司 HTML／Word、固定已结单集的真实试跑及禁网回放。真实包、请求、回答、报告、逐单复核全部仅写 `~/.noc7/`，仓库只留白名单汇总和结果说明。见 [业务口径试跑结果](../RESPONSIBILITY_LOCATION_BUSINESS_RESULTS.md)。

实际试跑受到提供方 503 和随后账户余额不可用的 402 阻断；专门责任锚点加入后的新提示词尚无完整真实在线验收，不以旧响应回放声称该项已验证。具体分母和阶段边界见结果报告。


## 后续试跑的调用预算

按用户充值后明确约束，试跑脚本在线仅允许 workers=1、provider.max_retries=0，每单至多一次，不重新请求旧基线、不自动补发。HTTP 402 立即结束；连续三张 503 或格式／结构／引用不合格结束，不能预提交后续单。每次实际 HTTP 尝试在本地审计记录 request_attempts，回放显式按零请求计数；未执行输入单列。合成与兼容验证禁网，旧／新规则读取同一回答对照。

本轮已取得当前提示词真实回答，不再属于“没有新提示词在线结果”的阶段；实际二十一次请求后遇 402，保留一张未请求，具体用量见结果报告。程序责任六项、地点一项中仍有一项客户责任误填和一项关键上门锚点待核，证明引用可定位及结构字段齐全仍不能证明动作语义。业务约束未因试跑而放宽，已知错误保留原样并单列，不补发、不伪造正确率；自动有记录状态仍不替代 NOC 人工审核。
