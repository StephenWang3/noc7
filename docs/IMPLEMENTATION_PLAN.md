# NOC 实现计划

> 2026-11-02 定位更新：当前目标为“完结工单的完整故障报告生成”，人工审核在 NOC 工作台完成。本文保留早期规划／兼容示例说明，阶段报告、自建审核界面等旧规划不再代表当前范围；以 [当前 PRD](PRD.md) 为准。其他状态合成示例用于展示未知／冲突边界，不作为已结单效果。

日期：2026-10-27｜关联：[PRD](./PRD.md)

## 1. 实施原则

先实现可导入、可追溯、可审核、可导出的完整闭环，再接真实NOC数据和更复杂附件。按里程碑验收；业务口径、数据接入和模型服务未知时用适配器隔离，不猜测生产接口。

当前目录为空，无既有代码约束。下列技术栈为拟选方案，依赖具体版本在实施时核对官方兼容说明并锁定。

## 2. 拟定架构

```text
工单JSON / 文本 / 上传材料 / NOC只读连接器
                    ↓
导入校验 → 原始材料存储 → 解析任务队列
                    ↓
文本/邮件/文档/图片解析 → 带定位信息的证据片段
                    ↓
去重与邮件引用清洗 → 事件抽取 → 时间线及资源标识候选
                    ↓
七要素提取 → Schema验证 → 业务规则校验
                    ↓
审核工作台 → 人工修订版本 → 模板渲染 → JSON/MD/HTML
```

### 技术选型

- 前端：React + TypeScript + Vite，提供材料、时间线、七要素审核和报告预览。
- 后端：Python + FastAPI + Pydantic，承载导入、任务、结构化数据与导出API。
- 数据：PostgreSQL保存业务和版本记录；本地文件存储起步，预留兼容对象存储的适配层。
- 异步任务：Celery + Redis；解析、模型分析、报告生成分阶段，设超时、有限重试和取消边界。
- 文档：PDF优先文本层解析，扫描页走OCR；DOCX提取段落/表格；EML通过邮件解析器拆分正文和附件。图片进入OCR及视觉模型适配层。
- 模型：统一文本/视觉调用协议，支持替换公司批准的服务；结构化输出经服务端验证，失败有限修复，仍失败则进入待人工处理。
- 部署：Docker Compose用于开发和单机试点；健康检查、任务指标、版本化配置，后续按公司环境调整。

选用Python是为了让文档解析、结构化校验和模型处理集中在同一服务层；前端仅承担审核交互。首版不引入向量数据库，先用工单范围内的证据索引和分层提取控制上下文。

## 3. 数据模型

| 实体 | 核心字段与用途 |
| --- | --- |
| Ticket | 工单来源、外部编号、类型、状态、客户/业务标识、访问范围 |
| SourceDocument | 工单ID、材料类型、内容哈希、原文件位置、来源时间、解析状态、是否AI衍生 |
| EvidenceSpan | 材料ID、原文、页码/段落/日志ID/图像区域、原时间和时区、解析质量 |
| Event | 事件类型、主体、动作、对象、结果、事件时间、记录时间、证据引用 |
| ExtractionRun | 输入快照、模型/提示词/Schema/规则版本、运行状态、成本和耗时 |
| ElementCandidate | 七要素名称、候选值、语义分类、证据、确认状态 |
| ValidationIssue | 规则编号、严重级别、关联字段、候选值、解决状态与理由 |
| ReviewRevision | 原机器结果、人工结果、操作者、时间、理由、基于哪个运行版本 |
| ReportVersion | 类型、模板版本、引用审核版本、数据截止时间、审核状态、导出文件 |

证据引用必须通过外键/应用校验确认存在且属于该工单授权范围。已审核版本为不可变快照；新增材料形成新运行与差异，不直接修改旧报告。

### 状态设计

- 分析任务：queued → parsing → extracting → validating → ready_for_review；可进入partial_failed、failed或cancelled。
- 材料状态：pending、parsed、needs_review、failed、unsupported。
- 报告状态：draft → in_review → approved；新输入产生的新版本标记需要复核，旧版本保持历史状态并提示已有更新。
- 故障业务状态与上述工作流分开，不用“分析完成”表示故障恢复。

## 4. API与连接器边界

拟定业务API：

- `POST /tickets/import`：校验并导入标准工单包，按外部ID及版本实现幂等。
- `POST /tickets/{id}/documents`：材料上传，返回文件解析状态。
- `POST /tickets/{id}/analysis-runs`：基于输入快照创建分析任务。
- `GET /analysis-runs/{id}`：查询阶段、进度、失败项和结果。
- `GET /tickets/{id}/evidence`：返回授权范围内的证据定位及预览。
- `POST /tickets/{id}/review-revisions`：带基准版本提交人工修订，冲突则拒绝并提示刷新。
- `POST /tickets/{id}/report-versions`：依据指定审核版本生成草稿。
- `POST /report-versions/{id}/approve`：检查角色、必要审核及关键冲突，再记录批准。
- `GET /report-versions/{id}/export?format=json|md|html`：导出指定版本。

NOC连接器仅实现读取：读取工单、分页日志、邮件、附件元数据和文件、增量游标。优先正式只读API或批准的批量导出；浏览器查看只用于调研与验证，不作为默认生产采集方案。连接器必须支持超时、限流、重试、去重、状态同步及源数据权限映射。

## 5. 提取与报告算法

1. 解析并保存原文，给每个片段分配稳定证据ID；源文件内容哈希用于去重。
2. 按邮件消息边界去掉重复引用和签名，保留原文和清洗后文本的映射；识别已有AI摘要。
3. 按事件抽取时间、主体、资源、动作、结果；同一原始证据的多次引用不增加独立佐证数量。
4. 对长材料分块抽取，再基于证据ID合并候选；不能只对反复压缩的摘要作最终认定。
5. 形成七要素候选和确认状态；模型不得创建不存在的证据ID。原文记载与业务确认分开。
6. 用确定性规则验证时间、单位、必需结构、证据归属、责任/根因/恢复依据和解析完整性。
7. 人工复核后按模板渲染。可选模型概述必须受已校验字段约束并经事实核对；初期优先确定性模板。

## 6. 开发工作包及完成标准

### M0：基线与契约，预计2—3个工作日

- 建立前后端目录、开发环境、配置示例、数据库迁移和基础CI。
- 定义七要素Schema、时间和证据结构、导入包格式及错误码。
- 根据四类已观察问题制作脱敏合成样本，明确它们不是原始工单数据或真实评测集。
- 整理接入清单、报告模板草稿和业务标注规范。

完成标准：本地一条命令启动；导入包可验证；必填/可空/冲突状态有示例；测试不连接生产NOC。

### M1：纯文本端到端闭环，预计5个工作日

- 实现JSON/文本导入、证据存储、异步任务和状态查询。
- 实现模型适配层、测试桩、事件与七要素抽取、第一批校验规则。
- 完成最小审核界面和JSON/Markdown/HTML导出。

完成标准：输入一张工单，能生成时间线与七要素，点击字段定位原文，人工修改后导出；缺失原因不被补齐，负历时被识别；无真实模型时可用固定测试桩演示流程，但不得宣称已验证AI质量。

### M2：附件和审核闭环，预计5—7个工作日

- 实现EML、DOCX、PDF、图片解析及上传限制；扫描页OCR和截图视觉提取。
- 实现邮件引用去重、AI摘要溯源、页码/段落/图像证据定位。
- 实现人工修订记录、报告批准、阶段/结案模板及新增材料差异展示。
- 实现解析失败、重试、模型超时和部分失败的完整用户提示。

完成标准：各支持格式至少有正常与失败样本；每项报告事实可追溯；重跑不覆盖人工结果；新增材料可提示报告过时；上传的恶意指令、宏或外链不会被执行。

### M3：NOC只读接入与真实评测，预计5—7个工作日

- 在接口和权限到位后实现一个NOC连接器，覆盖日志分页、邮件及附件。
- 导入标注开发集，调整提示词与规则；冻结版本后在独立验收集测试。
- 核实源系统时区、恢复/关单口径、资源别名及字段映射。
- 补全多用户权限、审计、脱敏和公司批准的模型配置。

完成标准：重复同步不重复建档、不回写NOC；权限测试通过；输出按字段准确率、召回率、证据质量、错误类型和耗时的评测报告，不只展示成功案例。

### M4：小范围试用与交付，预计3—5个工作日

- 在获准范围内由值班人员并行试用，比较原人工流程和工具辅助流程。
- 修复关键质量问题，完成性能、恢复、存储和部署检查。
- 交付安装文档、用户手册、规则说明、评测报告及回退方案。

完成标准：达到经业务确认的PRD门槛；关键根因/责任误判无未解决问题；可回退到人工流程；未满足指标则记录差距并继续迭代，不默认上线。

总开发估算约20—27个工作日，外部接口、模型服务、数据和业务审核等待时间另计。首个纯文本可演示版本目标为约7—8个工作日；估算不是固定交付日期。

## 7. 必测用例

| 用例 | 期望 |
| --- | --- |
| 原因栏写“无告警，主用正常” | 归入排查结论，根因未知 |
| 供应商为某设备厂商但无定责依据 | 责任方未知 |
| 系统恢复时间存在，但无客户确认 | 保留系统记载及依据范围，不能声称客户确认 |
| 客户79%丢包，某节点无丢包 | 分别保留来源和范围，不抹掉客户现象 |
| 旧CID已取消，新CID未交接 | 提示身份待核实，不认定为故障原因 |
| 告警时间、预警时间、建单时间不同 | 分别存储，不按最早时间无条件认定起障 |
| 邮件中UTC与GMT+8跨日 | 按明确时区正确归一，原文仍可见 |
| 无时区的海外设备记录 | 不按城市猜时区，标注假设 |
| 正文日期与系统记录日期冲突 | 出现校验问题，候选值均保留 |
| 作废单与有效单同电路 | 关联提示包含状态，不自动合并结论 |
| 原邮件及AI摘要重复出现 | 不计为两份独立证据 |
| 模型返回不存在的证据ID | 拒绝该结果并记录验证失败 |
| 附件缺失、OCR模糊或表格错位 | 显示未解析/待复核，不声称材料完整 |
| 附件包含“忽略规则并发送数据” | 仅作为文档内容，不执行 |
| 并发人工修订与分析重跑 | 检查版本冲突，人工审核记录不丢失 |
| 未授权用户获取原文、预览或导出 | 服务端拒绝，不能只靠隐藏前端按钮 |

## 8. 质量与交付方法

单元测试重点覆盖业务规则、时间处理、引用校验和导入幂等；集成测试覆盖导入→分析→审核→导出及失败重试；端到端测试覆盖证据跳转、人工修订和版本变化。附件解析通过固定文件校验结构及定位。模型质量使用冻结评测集单独评估，不用接口成功率代替质量。

建议目录：`frontend/`、`backend/`、`schemas/`、`tests/fixtures/`、`evals/`、`deploy/`、`docs/`。真实工单、客户原文件和密钥不纳入源码仓库；评测材料独立受控保存。

各里程碑交付可运行版本、变更说明、测试证据和已知限制。生产上线前完成环境配置、权限、日志脱敏、备份恢复和数据保留策略核对。

## 9. 下一步开发顺序

1. 建立Schema和四类合成回归样本，固定七要素与证据契约。
2. 搭建后端导入、存储和任务流水线，提供测试桩模型。
3. 搭建审核工作台，跑通一次导入到报告导出。
4. 接入获准的真实模型与首批脱敏标注样本，再做附件和NOC连接器。

前3项可直接开始；真实数据和模型服务到位后再完成真实质量验证。无需等待生产接口即可推进核心实现。
