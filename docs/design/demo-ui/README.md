# 演示页面设计稿：选择工单 → 七要素与原文出处 → 下载公司报告

状态：**设计稿，待用户确认**。确认前不实现前端；前端另开任务。日期：2026-10-29。

## 怎么看

直接打开 `index.html`（在变更预览里点预览按钮，或本机双击）。纯静态，无需服务，按 1280×720 投影设计，页面本身不滚动，只有面板内部滚动。

| 想看什么 | 怎么打开 |
| --- | --- |
| 画面 1 选择工单 | `index.html` |
| 画面 2 七要素与出处 | 选一张单；或 `index.html#/2/SYN-S09/cause` |
| 「AI 建议，待确认」 | `index.html#/2/SYN-S09/location/ai` |

| 工作台嵌入形态 | `index.html?ticket=SYN-P01&embed=1` |

七要素页按 `↑/↓` 切换要素，`Esc` 关抽屉。

## 三个画面

**① 选择工单**：顶部一条流程图，说明“原始工单 → 大模型预处理 → 七要素+出处 → 公司报告”，最右一格虚线框写明“人工审核在 NOC 工作台完成，不在本页”。下面两个标签页：「本地工单包」（卡片，每张带 7 格状态色条和待核实数）、「由 NOC 工作台传入」（输入工单号）。

**② 七要素与原文出处**（核心页）：左侧 7 要素导航，每项一行：名称、状态、取值预览、待核实数、有无 AI 建议。右侧一次只看一个要素，分三个标签页：

- 结论与出处：左边是结论（或“不填写”的原因、或并列的矛盾说法）和「待核实」卡片；右边是原文出处卡片，结论引用的那句话**黄色高亮**，点结论里的证据编号会定位并闪动对应卡片。
- 全部候选：系统读到的所有说法，标明谁说的（客户反馈/检查显示/现场工程师称……）、含义（“建单时间，不是故障时间”“排查结论，不是根因”）、是否被采用。
- AI 建议，待确认（仅责任方、地点）：虚线紫框，明说“不是结论、不进报告”，每条建议带引文和“原文核对通过 / 待核对：引文在原文里找不到”。

页面顶部有常驻图例（可收起），六个词各一句人话。

**③ 公司报告与下载**：左边按公司模板 11×4 表格预览（与 Word 同源）；右边先是“草稿·未经人工审核”和下载按钮（Word 为主、网页版为辅），再是“下载前检查”：列出报告里每处【待核实】，点“→ 要素名”回画面 2 对应要素。

## 给不懂 NOC 的评委的三条设计

| 问题 | 做法 |
| --- | --- |
| 四种状态一眼分清 | 颜色之外一定有图标和文字：✓ 已确认（绿）、● 有明确记录（青）、○ 未知（灰虚线）、≠ 矛盾（红）。图例每项一句人话，例如未知＝“材料不足，系统宁可留空，也不猜”。 |
| 出处怎么“一眼看懂” | 每条结论旁直接放原文卡片：编号、来源（“工单字段·故障发生时间”“处理过程·第 5 条”“PDF 附件·第 1 页”）、谁说的、高亮句子。证据编号 `M02/log:5` 在页脚解释一次，不要求读懂。 |
| 待核实 vs AI 建议 | 两种不同的东西，所以外观完全不同：「待核实」是琥珀色实线卡片，写“为什么要核实”（“恢复没有客户确认：只有系统记录说已恢复，没人确认业务真的好了”），并保留系统原话；「AI 建议」是紫色虚线框，在独立标签页里，永远不和结论混排。严重程度三档：严重冲突/待核实/提示。 |

页面不出现“采纳/驳回/修改”按钮。这是课题边界：人工审核在 NOC 工作台里做。页面只放一个「在 NOC 工作台中审核 ↗」，点击发出事件。

## 和 NOC 工作台的接口（回答开放问题 2）

**选了方案 B：页面不关心工单从哪来，所有入口最后都调用 `openTicket(工单号)`，工作台只需要传工单号。**

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| A 只选本地已导出的包 | 页面扫描目录列出工单包 | 最简单；但工作台要集成时得重做入口 |
| **B 本地选择 + 工作台传工单号（推荐）** | 两个入口并存，同一个 `TicketSource` 接口；工作台用链接、iframe 或 `postMessage` 传工单号 | 多一层接口，换来前端不用改；演示时两种入口都能现场点 |
| C 工作台推送整份分析结果 | 工作台把 JSON 传给页面 | 页面零后端；但工作台必须懂七要素格式，格式一变两边都要改 |

约定（抽屉“接入 NOC 工作台”里可现场演示，含实时事件日志和“模拟工作台传入”按钮）：

- 入口：独立使用；链接 `?ticket=<工单号>` 或 `#/2/<工单号>/<要素>`；iframe 嵌入加 `?embed=1`（隐藏品牌栏）并接收 `postMessage({type:"noc7.open", ticket_ref})`。
- 数据：页面只吃一种数据，`AnalysisResult`（`schemas/analysis-result.schema.json`），公司报告表格来自同一份结果。拟定接口（沿用 `ARCHITECTURE_OPTIONS.md` 方案 A 的 FastAPI）：`GET /api/tickets`、`GET /api/tickets/{ref}/analysis`、`GET /api/tickets/{ref}/company-report.docx|.html`。路径由前端任务定稿。
- 出口事件：`noc7.ticket.opened`、`noc7.report.downloaded`、`noc7.review.requested`。
- 接缝在代码里：`app.js` 的 `TicketSource`（`list()`、`get(ref)`）。本稿用 `demo-data.js` 实现，真实前端换成 `fetch` 即可，画面代码不动。

## 示例数据（只用合成数据）

`demo-data.js`、`samples/` 由 `build_demo_data.py` 从 `fixtures/bundles/` 的 5 张合成单（SYN-P04、S09、P01、S06、S02）经真实流水线（规则基线）生成：

```sh
uv run python docs/design/demo-ui/build_demo_data.py
```

- `samples/` 里的 Word 和网页版是 `write_company_docx` / `render_company_html` 的真实输出，页眉用空配置，不读取本机 `~/.noc7/report_profile`。页面上点“下载 Word”拿到的就是这些文件。
- 五张单合起来覆盖：已确认（P04 的责任方/原因/结束时间）、大量未知（S09）、矛盾（P01 结束时间、S06 起障时间、P04 故障地点）、重复记录合并（S02）。
- **「AI 建议」是例外：规则基线不产生建议，S09 的两条建议是设计稿手写的**，结构仿 `BusinessSuggestion`，页面上标了“示例”。第二条故意引了一句原文里不存在的话，用来演示“待核对”。真实建议要等模型链路接入。
- 没有任何真实工单内容。

## 已知问题和需要前端任务处理的点

1. **P04 的故障地点被规则基线判成“矛盾”**：处理记录和 PDF 附件对同一个人井写了两种说法（都含 `SYN-MH-0102 东侧约 15 m`），基线不会合并它们。这是当前真实输出，设计稿照实展示，没有改数据；答辩时可以讲成“系统不擅自合并说法”，但它也是基线的一处缺陷，值得单独记录。
2. 「分析中」状态未画：本稿的工单都已预处理好。正式版选中工单后若要现场调模型，需要进度和失败状态（`ExtractionRejected` 的拒绝原因）。
3. `postMessage` 目前不校验来源。前端实现必须校验 `e.origin` 并把目标域名写死。
4. 页面里的状态、问题码、候选类别翻译词表在 `app.js` 顶部（`ISSUE`、`TIME_KIND` 等），只覆盖这 5 张单出现过的码；其余码会退回显示系统原话。全量词表在前端任务里补。
5. 画面 3 的预览是 `build_company_report` 的结构化输出重排的，不是 iframe 嵌 `company_report.html`；正式版建议由后端直接给 HTML 片段，避免两处排版漂移。
6. 窗口宽度低于约 1000 px 未适配（演示场景是投影或桌面）。
