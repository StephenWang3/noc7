# 0003 工单包格式与 A1/A2 并行契约

- 日期：2026-10-27
- 阶段：A0
- 状态：已采纳
- 相关：`docs/BUNDLE_FORMAT.md`、`docs/CONTRACTS.md`、`src/noc7/bundle.py`、`src/noc7/parsers/`、`src/noc7/providers/gate.py`

## 背景

A0 合入后，A1（文本链路）和 A2（附件）由另一个 agent 同时开发。如果输入格式、证据编号、问题代码或依赖声明没有在 A0 定死，两条线会同时改同一批文件，合并时冲突，甚至产生两套不兼容的格式。

另外两条硬约束：

- 真实工单不能进仓库，也不能发给外部服务；
- 调研发现处理过程顶层的“有附件”标志不可靠（S10 标志为 false，实际有附件），附件必须逐条登记。

## 可选方案

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 1 直接读源系统 JSON | 解析器各自读导出的原始数据 | 不用定义格式 | 合成样本、上传、导出三种来源各一套代码；漏件无法发现 |
| 2 工单包（清单 + 文件） | `manifest.json` 登记每份材料的类型、路径、哈希；ticket.json、process_log.json 固定结构；附件按文件存放 | 来源无关；哈希防篡改、清单防漏件；数据分级写在清单里 | 导出脚本要多做一步整理 |
| 3 数据库导入 | 一开始就入 SQLite | 查询方便 | 合成样本不便于审阅和版本管理 |

并行开发方面：

| 方案 | 做法 | 缺点 |
| --- | --- | --- |
| a 按功能拆、共享解析器目录 | 两条线都往 `parsers/` 加代码 | 共享注册文件、编号规则冲突 |
| b 按材料类型拆，证据片段是唯一接口 | 每种材料类型只归一条线；两条线只交换 `EvidenceSpan` | 需要提前定好片段结构和编号规则 |

## 选择及理由

选 2 + b。

1. **工单包**：清单登记每份材料的 sha256 和大小，导入时逐一核对；目录里有未登记的文件也拒绝。数据分级 `synthetic` / `real` 写在清单里，真实工单包放在仓库里会被拒绝导入。处理过程每条记录列出实际附件编号，顶层“有附件”标志只留档，不一致时只报提醒。
2. **按材料类型分工**：`PARSER_OWNERSHIP` 写明哪种材料归哪条线，注册表拒绝重复注册。
3. **证据编号带材料前缀** `M03/msg:1`：每个解析器只在自己的材料编号下命名，两条线不可能撞号。`ParseOutput` 拒绝不属于本材料的片段。
4. **默认注册表**按包名自动加载 `noc7.parsers.text`（A1）和 `noc7.parsers.attachments`（A2）。包不存在时由 `UnsupportedParser` 兜底，所以 A1 不用等 A2 就能跑通全部合成样本，两条线也都不需要改注册代码。
5. **外发闸门放在 A0**（原计划在 A2）：A1 的文本模型和 A2 的视觉模型/OCR 都要用，放在任一条线都会让另一条线等待或各写一套。外部服务放行真实数据必须写明批准依据，没有绕过开关。
6. **依赖一次声明**：BeautifulSoup、Jinja2、PyMuPDF、python-docx、Pillow 在 A0 写进 `pyproject.toml`，两条线不必同时改 `pyproject.toml` 和 `uv.lock`（锁文件冲突很难手工合并）。
7. **标准答案用“锚点”而不是证据编号**（见 0004），解析器怎么切片段都不影响标准答案。

## 后果与代价

- 导出脚本（A1 之后）要把源系统数据整理成工单包，多一步工作，但同时是一次完整性检查；
- EML 归 A2，EML 里的邮件正文如需复用 A1 的消息切分函数，只能调用，不能改；
- 契约变更规则见 `docs/CONTRACTS.md` §8：只追加；不兼容变更要另写决策记录并同步更新标准答案。
