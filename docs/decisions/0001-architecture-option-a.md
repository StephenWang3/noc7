# 0001 采用方案 A：Python 轻量单体，“证据优先”流水线

- 日期：2026-10-27
- 阶段：A0 之前（架构选型）
- 状态：已采纳（用户 2026-10-27 选定）
- 相关：`docs/ARCHITECTURE_OPTIONS.md`（完整的方案比较）、PRD §10

## 背景

课题要证明的是“杂乱工单 + 附件 → 带证据的七要素 JSON → 规则校验 → Markdown/HTML 报告”这条链路能跑通、能核对、效果能量化。调研（`docs/NOC_RESEARCH_SUPPLEMENT.md`）发现七要素经常不能直接照抄工单栏位：原因栏是排查结论，责任方只是处理部门，恢复时间没有客户确认，关键数值只在截图里。AI 服务还没有获批，真实工单不能外发。

## 可选方案

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A 轻量单体 | Python 一个进程：FastAPI + Pydantic + SQLite + Jinja2/HTMX；核心算法是独立的包 `noc7` | 一条命令启动、可离线演示；精力集中在证据融合、校验、附件理解和评测 | 不支持多用户并发；HTMX 交互上限低于 React |
| B 生产级试点 | React/TS + FastAPI + PostgreSQL + Celery/Redis + Docker | 接近生产形态 | 基础设施工作挤占核心算法和评测；需要部署环境和账号 |
| C 嵌入 NOC 的浏览器扩展 | 在 NOC 页面里增强现有“业务故障报告” | 观感好 | 要往生产 NOC 写入；页面改版即失效；演示依赖生产环境 |

## 选择及理由

选 A。

1. 用最少的基础设施覆盖整条链路，每一步都能在本机复现，答辩时可以离线演示；
2. 核心包 `noc7` 不依赖 Web 框架、存储和任务队列，以后要演进到 B 只需要替换外围；
3. Pydantic 一处定义七要素结构，同时用于约束模型输出、校验结果和导出 JSON Schema；
4. “证据优先”：先把材料切成带编号的片段，模型和规则只能引用编号，编造的引用能用程序查出来。

## 后果与代价

- 单机、单用户，PRD §10 允许这样做；
- 先用 `rules`（纯规则）和 `replay`（录制回放）两种不调用外部服务的提供方开发，模型接入可以晚于流程打通；
- 外发闸门写在代码里（见 0003），不靠约定。
