# 八例责任方与地点的分阶段调查

本轮只调查，未修改产品代码、提示词、冻结集或评分规则，未请求 DeepSeek。复用 #14 保存的八份 HTTP 原始响应与结构补全、重算前后快照，逐例离线复算；八例快照逐项一致，七例通过、一例拒绝的结果也一致。

**主要发现：七张地点单均生成了包含冻结要点、且能在所引原文找到的候选，随后全部因本地地点角色识别返回空而被删除；其中四张的已填结论被清空。唯一责任单没有生成责任候选，相关文字被放入原因栏。** “两栏最终为零”不能解释为模型全部没找到。

这仍不等于模型七个地点答案都已达到业务确认标准：三例只给候选而未下结论；地点粒度、同事件重复及责任参考的语义仍需单列。历史分数不变：规则 0/8，DeepSeek 有效答复 0/7，另一例运行被拒。

## 材料与复核方法

先读取 #14 的任务与保存方案，再抓取其任务分支，核对扩样报告及本次相关重算、评分代码与当前分支无差异。沿用 [扩样报告](RESPONSIBILITY_LOCATION_SAMPLE_EXPANSION.md) 的冻结八例，九条未确认支持的参考不进入本轮分母。

真实资料仅在 `~/.noc7/`。原批次为 `~/.noc7/sample-expansion-it6b5svf/`；本轮新增私有目录为 `~/.noc7/investigation-8-20261029/`，没有覆盖原批次。逐单全文、证据、原始枚举、重算探针及拒绝定位分别在：

- `details.md`、`trace.json`：八例逐单追踪，含原文，仅限本机。
- `quote-checks.json`：两处引文空白差异的逐条检查。
- `source-hashes.json`：原冻结参考、选择文件、审计与结果的读取哈希。
- `investigate.py`：离线复核脚本；运行 `uv run python ~/.noc7/investigation-8-20261029/investigate.py`，不进行网络请求。

脚本以冻结包和审计实际请求中的证据重建上下文；请求专用的 `recorded_at` 元数据不属于 `EvidenceSpan`，构造对象时仅保留该类型声明的字段。重新执行结构补全、本地重算和引用校验，对照已存快照；逐候选检查原文子串、冻结要点及重算角色。下面仅列匿名代号与脱敏结论；代号沿用原冻结集，不表示连续编号或独立故障事件。

## 为什么本地规则看不到这些地点

`src/noc7/providers/text_ground.py` 的 `_ground_location` 对每个候选调用 `_location_of`；返回 `None` 就直接跳过该候选。已填结论的选中候选消失后，`_clear` 把状态改为未知并清空值、选中项及结论引用。因此规则和模型最终链路并非独立判断：模型最后仍要通过同一套规则的语义识别。

`src/noc7/extract/baseline.py:location_role` 当前主要承认中文“现场确认／故障点位于”及 `rfo_fault_points` 支持的英文格式。后者在 `fact_phrases.py` 中要求 `Location: Between … and …, 地区`，还要求邻近 `Reason for Failure/Outage:` 及故障词。

本批七例全部不满足这条入口格式：包括正文中的光缆切断区段、受故障影响区段、“故障位置在……”、距参照点若干公里和坐标表达。即使原文写了 RFO，也不等于符合这套标题与格式约束。三张同区段样本的自然语句含 `between`，但没有要求的 `Location:` 标题与逗号地区；另外的距离表达不是该格式。规则侧七例地点候选也均为零，漏在生成候选之前，而模型侧漏在生成之后的角色重算。

**本批没有证据证明地点是被否定、疑似或 RFO 整段排除误伤。** 对实际支持与候选逐项调用的角色均为空，RFO 匹配也为空；主因是识别入口未覆盖这些句式。材料中确有修复中、推测及其他链路的信息，但移除这些限定也不会补上缺失的格式入口。将否定规则全部放宽不能解决本批首要卡点，反而可能把其他故障或推测当作已定位事实。

E07 的英文设备故障句同样不在 `responsibility_claims` 当前的中文“客户原因／责任归属”模板中。它没有先匹配再被否定规则删掉。模型原因候选把明确设备故障和后一句可能的致损机制合在一起，标为疑似原因；需要区分两句的断言范围，但不能据此自动补出责任认定。

## E18 的拒绝来自哪里

离线重新调用 `validate_extraction` 得到与原审计相同的两项 `EVIDENCE_QUOTE_MISMATCH`：一项来自事件动作，另一项来自处理步骤，不是地点候选。

两段模型文字均将原邮件中的不换行空格 `U+00A0` 换成了普通空格。严格子串检查失败；仅在本机诊断中统一连续空白后，两段均成为原文子串。没有发现这两处拒绝由业务词语改写造成。当前接口按整单拒绝，所以其他栏位也不能输出。

这是单独的引用表示问题：即使将来修复空白核对，这张的地点仍会被当前角色规则删除；即使只修地点规则，后面的引文核对仍会拒绝整单。需要两个环节分别处理，不能把整单拒绝直接归因于地点引用错误。

## 打分与参考口径

评分器 `src/noc7/evaluation/score.py:compare` 先检查值是否为空，空值直接返回 `missing`，之后才检查状态、选中项角色和要点。七份有效结果的目标值均为空，故这次最终零分不是同义词匹配失灵。

诊断中直接将四份重算前已填地点值交给原比较函数，四份均为 `agree`。这是定位卡点的反事实检查，**没有经过完整最终校验，也不是修复后的成绩或准确率**。三份只给候选的地点单仍需决定是否采纳、以何种状态展示；不能把有要点的候选手动填成结论后当作模型已答对。

评分口径仍有三项问题需要后续单独审定：

1. **责任语义越界风险。** E07 的原句说明客户侧设备有故障，下一句说明接地可能致损；它并未明确说客户承担责任。#14 把它冻结为 `documented/claimed` 客户归因；本轮保留历史分数，但不沿用“这一例已明确具备责任依据”的强解释。设备故障所属侧与责任归属是否同一业务概念，需要业务确认。若不认可，应新建参考版本并将该责任事实另列，不能倒改旧分母，更不能为了它给英文模板直接补“客户责任”。
2. **要点不等于地点关系。** 当前要点主要是两地名，或数字＋参照点，不能完整校验方向、距离单位、“距站点”与“站点处”的差别。坐标、区段、城市、参照站点也不是天然同义词；一个宽泛线路段不能代替精确断点。未来参考宜分别标区段端点、距离及单位、参照对象、关系和粒度，再评价语义一致性。
3. **样本不等于事件数。** E03、E09、E10 使用相同区段和相近上游表述，可能共享故障；按工单可得三次观测，不能视为三种独立句式成功。七条地点参考也不能外推成总体准确率。

Spec 提及“距站点约十二公里被转述为站点处”的案例，核对后是原预审的 E14，**不在本次正式八例内**，属于此前九条未确认支持之一；还伴有芯数表述差异。原流程正确地拒绝了它的输入支持。本轮不将它计作模型遗漏。这个例子说明人工结案与原始 RFO 也可能不一致，不能靠共享地名或追加同义词消除差异。

## 三个可选改法

以下只是供选择的方案，没有实施，也没有修改接口或默认行为。

| 方案 | 具体变化 | 收益 | 代价与限制 |
| --- | --- | --- | --- |
| A：有限扩展现有规则 | 给自然英文故障区段、距离定位与坐标增加有上下文约束的识别；按分句区分明确故障与推测机制；单独处理可回溯的空白等价引用 | 沿用当前结论和报告接口，直接覆盖已定位的格式缺口 | 继续依赖规则覆盖；新句式仍可能漏。不能因设备在客户侧就定客户责任，不能简单关闭否定或整段校验 |
| B：保留模型语义，独立验证证据关系 | 模型输出故障描述、关系、粒度、原文范围与来源；校验器核对来源、引用、否定作用域、对象关系与跨事件混淆，不再用一套短语模板重做全部提取 | 减少“模型找到了又被模板删掉”，比单纯加句式更能保留不同表达 | 要设计关系验证与冲突处理，仍需评估误接纳；独立验证也不能证明供应商的业务断言一定正确 |
| C：展示“AI 建议，待人工确认” | 模型的责任方／地点建议及原文证据直接进入待确认区，不经规则重新判定其业务语义；人工可采纳、修改或驳回，记录操作与版本后才进入正式结论 | 用户能看到模型实际找到的内容和不确定性，停止因规则未识别就完全隐藏线索 | 增加人工审核负担，必须避免把建议混入已确认字段、评分或正式报告；直接展示全部模型结果会保留错误，因此仍需基本来源与显示保护 |

C 中的“直接展示”指不再用规则覆写模型的业务判断；包完整性、来源存在、展示转义、证据可追溯仍需保留。引文不匹配可以显示为待核对问题，不得包装为已核验引用；模型不能自行生成审核通过记录。建议区保留模型原断言、原始状态和归因来源，明确区分“某方声称”与系统／人工认定；用户采纳也不自动等于业务正式定责。

若目标是尽快让审核者看见可用线索，建议优先选择 C 的产品方向，同时以新参考版本澄清责任定义及地点关系；A 可作为受限对照，B 适合后续降低人工审核负担。新评估应分别统计候选有据率、正式结论一致率、引用拒绝原因和人工采纳／修改／驳回，不能继续用单一最终零分解释全部过程。新样本应包含否定、疑似、端点／告警点、相同地名不同距离、主备路径及多事件干扰，先冻结再运行。
